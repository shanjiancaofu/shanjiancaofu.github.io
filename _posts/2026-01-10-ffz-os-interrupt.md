内核进入 32 位模式后，如果只有一个不断运行的 `main` 函数，它还称不上完整的操作系统。键盘输入、时钟调度和系统调用都需要 CPU 能从当前执行流进入统一的中断处理入口。

## IDT 保存什么

中断描述符表 IDT 可以理解为“中断号到处理入口的映射表”。每个门描述符保存处理函数地址、代码段选择子、门类型和特权级。

内核初始化时先为每个向量建立描述符，再通过 `lidt` 装载 IDT 的地址与界限：

```text
低 16 位：IDT 大小减一
高 32 位：IDT 起始地址
```

这里的括号和位运算必须非常谨慎。项目曾因 IDT 操作数表达式错误导致用户线程无法运行。底层代码中，一个移位优先级错误就可能让 CPU 读取完全错误的表地址。

## 为什么还需要 8259A

IDT 决定 CPU 收到某个向量后去哪里执行，而 8259A PIC 决定外部硬件中断如何映射、哪些线路被屏蔽。

经典 PC 使用主从两片 8259A。初始化时需要发送 ICW 命令，设置主片和从片的向量起点、级联关系及工作方式。随后通过 OCW1 屏蔽或打开具体 IRQ。

例如时钟通常连接 IRQ0，键盘连接 IRQ1。只建立 IDT 入口但没有在 PIC 中打开对应线路，处理函数仍不会被调用。

## 中断入口为何需要汇编包装

CPU 进入中断时只自动压入部分现场。为了让 C 函数安全执行，汇编入口还要保存通用寄存器和段寄存器，并按统一格式补充中断号或错误码。

返回时则按相反顺序恢复现场，最后执行 `iret`。因此 C 处理函数看到的是一个稳定的中断栈，而不是每种异常各不相同的零散布局。

## 时钟中断驱动调度

PIT 按固定频率产生 IRQ0。时钟处理函数更新全局 tick 和当前线程已运行时间；当时间片耗尽时调用调度器。

```text
PIT tick
  → IRQ0
  → 时钟中断处理
  → 当前线程 ticks--
  → ticks 为 0 时 schedule()
```

项目调试中曾因测试键盘时屏蔽了 timer 中断，导致调度函数再也没有机会执行。这个现象提醒我：多线程代码没有切换，不一定是调度器本身有问题，也可能是它的驱动事件从未到达。

## 关中断不是越久越安全

内核通过关中断保护一些短小的关键区，例如修改线程状态和就绪队列。关键区结束后必须恢复进入前的中断状态，而不是无条件开中断：

```cpp
enum intr_status old = intr_disable();
// 修改共享内核状态
intr_set_status(old);
```

如果持有关闭状态太久，时钟、键盘和其他设备事件都会延迟，系统表现为卡顿甚至假死。关中断只适合不可睡眠、执行时间可控的操作。

## 异常、硬件中断与系统调用

三者最终都可以通过 IDT 进入内核，但来源不同：异常由当前指令触发，硬件中断来自外设，系统调用则是用户程序主动请求内核服务。

统一入口便于保存现场和分发，但处理策略必须区分。例如页错误需要检查故障地址，时钟中断要向 PIC 发送 EOI，系统调用则要验证编号和参数。

中断系统搭好后，内核才真正拥有响应外部世界和抢占当前任务的能力。理解 IDT、PIC、汇编入口与 C 处理函数的分工，也为后面的线程调度打下了基础。
