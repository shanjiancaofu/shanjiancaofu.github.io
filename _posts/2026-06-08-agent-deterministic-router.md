车载 Agent 既要回答开放问题，也可能控制相机、媒体和车辆功能。这两类请求不能共享同一条不确定的决策链：大模型可以生成自然语言，却不应该根据自由文本直接构造硬件动作。

项目把动作链设计为“归一化、确定性路由、类型化动作、执行校验”四个阶段。

## 先把文本变成稳定输入

ASR 的输出可能混有多余空格、全角字符、大小写差异和句末标点。`TranscriptNormalizer` 负责进行有限且可解释的归一化：

- 去除首尾空白；
- 折叠连续空白；
- ASCII 转小写；
- 全角 ASCII 和全角空格转半角；
- 处理常见中英文标点；
- 保留中文 UTF-8 内容。

归一化只消除表现差异，不尝试猜测用户意图。它不会把任意近义句改写成某个动作。

## 使用正向整句白名单

路由器只接受经过审核的完整命令，例如：

```text
打开相机
请打开摄像头
open camera
播放音乐
查看车辆状态
```

匹配使用整句相等，而不是子串搜索。只有命中固定 `CommandEntry` 时，才返回确定的 `VoiceIntent` 与 `VoiceAction`。

```cpp
struct DeterministicCommandRoute {
  VoiceIntent intent{VoiceIntent::kUnknown};
  VoiceAction action{VoiceAction::kNone};
};
```

其他文本统一返回 `Unknown + None`，随后可以交给本地 LLM 生成普通回答，但不能执行动作。

## 为什么子串匹配不安全

假设路由器只查找“打开相机”，下面这些句子都会产生歧义：

```text
不要打开相机
如果停车以后再打开相机
我没有说打开相机
打开相机然后播放音乐
```

依赖否定词黑名单也不可靠，因为自然语言表达方式太多。正向整句白名单虽然覆盖范围更小，却能清楚回答“哪些输入一定会触发什么动作”。

## Fail Closed 的含义

Fail Closed 表示系统遇到否定、条件、延期、多个动作、未知参数或无法解析的表达时，默认不执行硬件动作。

它与“尽量理解用户”并不冲突。Agent 可以回复“目前无法执行这条组合命令，请一次说一个操作”，但不能为了体验流畅而猜测一个最接近的动作。

在车辆场景中，少执行一次可以重试，误执行一次却可能带来真实风险。

## 动作必须是类型化的

当前动作集合只包含已有消费者的能力：打开相机、播放音乐和查询车辆状态。路由器不会返回 shell 命令、可执行文件路径、任意 RPC 名称或自由生成的 CAN 数据。

```text
Transcript
  → Normalizer
  → DeterministicCommandRouter
  → VoiceAction
  → ActionDispatcher
```

参数化动作也不能先开放一个字符串接口再慢慢补校验。只有执行方、参数结构、范围限制和测试全部存在后，才应该加入动作类型。

## LLM 在能力结构上不可达

本地 LLM 客户端的接口只返回 `response_text`，不持有 `ActionDispatcher`，也不暴露工具调用。即使模型输出一段看起来像 JSON 的动作描述，系统也只会把它作为文字处理。

这是能力隔离，而不是提示词约束。提示词可以帮助模型生成更合适的回答，却不能替代代码接口上的最小权限。

## 安全动作还需要最终校验

命中白名单不代表可以无条件执行。`ActionDispatcher` 仍应检查运行模式、车辆状态、权限和 deadline。例如某个动作只允许驻车时执行，就必须在接近硬件的一侧再次判断。

语音“停止”也不能替代物理急停、底盘安全状态机、通信超时和硬件看门狗。上层 Agent 只是交互入口，不是安全系统的唯一防线。

确定性路由牺牲了一部分语言覆盖率，却换来了可审计、可测试和可解释的动作边界。对于能够影响真实设备的 Agent，这是一笔值得的交换。
