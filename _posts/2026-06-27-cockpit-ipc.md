智能座舱同时处理车辆状态、音频 PCM、相机图像、控制命令和诊断信息。如果为了“统一技术栈”把所有数据都塞进一种消息系统，往往会增加复制、延迟和故障点。更合适的方法是根据数据大小、频率、线程关系和可靠性需求选择通信机制。

## 先区分控制面与数据面

控制面的数据量小，关注可理解的请求、状态和错误：

- 模块启动与停止；
- 配置、健康状态和指标；
- 拍照、播放等低频命令；
- 车辆状态和识别文本。

数据面则持续传输大块数据，例如音频帧、相机像素以及未来的模型张量。它更关注固定容量、低复制和背压策略。

## 当前系统的分层选择

```text
同线程同步调用        → 普通函数
同进程低频事件        → callback / MessageBus
同进程连续单向流      → SPSC RingBuffer
跨进程控制            → gRPC unary
跨进程小消息流        → gRPC streaming
跨进程音频帧          → Unix SOCK_SEQPACKET
跨进程相机图像        → POSIX shared memory
```

这里没有“最先进”的单项技术，只有更匹配数据特征的组合。

## 音频为什么使用有界流水线

音频采集线程每 20 ms 产生一帧 PCM。它不能等待语音识别，也不应该直接执行可能阻塞的 socket I/O。系统先写入 SPSC 环形缓冲，再由独立发布线程通过 Unix `SOCK_SEQPACKET` 发送给 Agent。

```text
ALSA capture
  → SPSC RingBuffer
  → 有界发布队列
  → SOCK_SEQPACKET
  → Agent / VAD / ASR
```

当消费者跟不上时，队列丢弃旧帧，并在后续帧中标记 `discontinuity` 和 `dropped-before`。实时音频中，保留几秒前的积压通常不如尽快恢复到当前数据有价值。

`SOCK_SEQPACKET` 还保留消息边界，接收方不会把半个音频包误当成完整帧。固定头部携带版本、序号、采样时间、采样率和样本数，便于检测断流与协议不匹配。

## 车辆状态适合 gRPC streaming

车辆状态体积较小、频率相对低，又有多个消费者，因此使用类型化的 protobuf 和 gRPC streaming 更容易维护。原始 CAN 帧仍由 Vehicle Driver 独占解析，不直接暴露给 UI 或语音模块。

这种边界让消费者依赖产品语义，例如车速、挡位和故障状态，而不是依赖具体 CAN ID 与位布局。

## 进程内 MessageBus 的边界

轻量 MessageBus 适合相机状态、帧元数据和模块事件。它支持 topic 订阅、固定容量队列、丢弃计数和 metrics，但不跨进程，也不传输相机像素。

如果把大图像放进通用事件总线，所有订阅者都可能触发复制，慢消费者还会拖累生产者。像素数据应该走共享内存，事件总线只通知“有新一代数据可读”。

## 有界是比“绝不丢数据”更真实的合同

无限队列只是把过载推迟成内存耗尽。车端长运行系统必须为每条链路回答三个问题：队列最多多大、满了丢新还是丢旧、消费者如何知道发生过丢弃。

对实时预览和语音采集，常见策略是保留最新数据；对控制命令则不能静默丢弃，需要返回失败或超时；对诊断录包则应记录缺口并保证文件可恢复。

通信架构的核心不是协议数量越少越好，而是模块之间交换的每类信息都有清晰的容量、时序和失败语义。
