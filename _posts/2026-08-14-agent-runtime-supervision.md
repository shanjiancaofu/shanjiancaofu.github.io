端侧 LLM 通常拥有独立运行时、模型文件和较大的内存占用。把推理引擎直接链接进 Agent 进程，会让符号依赖、崩溃隔离和资源回收变得复杂。项目选择让 `llama-server` 作为 Agent 的子进程运行，再由 Agent 管理它的完整生命周期。

## 为什么不增加第二个 systemd 服务

整个座舱只保留一个系统级入口：`cockpit-navigator.service`。Navigator 管理 Agent 模块，Agent 再管理只属于自己的推理子进程。

```text
systemd
  └── cockpit-navigator
      └── agent
          └── llama-server
```

如果把 `llama-server` 变成独立 systemd 服务，模型版本、配置切换和 Agent 生命周期就会分散到两个管理平面。由资源拥有者管理子进程，更容易保证启动和退出顺序。

## 启动前固定所有输入

进程配置包含可执行文件、模型路径、模型别名、监听地址、上下文长度和 GPU offload 层数。产品环境不在启动时下载模型，也不从任意用户输入拼接参数。

运行时和模型分别版本化，manifest 至少记录版本、commit、模型 ID、量化方式、SHA-256 和许可证。准备阶段完成校验，设备启动只消费已经审核的本地文件。

服务仅监听 `127.0.0.1`，Agent 不把推理接口暴露到外部网络。

## Spawn 成功不代表服务可用

`fork/exec` 返回成功只能说明进程被创建，模型可能仍在加载，也可能因内存不足立即退出。因此启动过程还要等待 readiness：

```text
检查配置和资源
  → spawn 独立进程组
  → 周期探测 HTTP health
  → readiness 成功
  → Agent 开始接受 LLM 请求
```

整个过程受 `startup_timeout` 限制。如果服务在期限内没有就绪，Agent 应报告明确错误并回收子进程，不能永远卡在启动阶段。

## 运行期间持续健康检查

进程存在并不代表能够推理。监控线程按固定间隔进行健康探测，连续失败达到阈值后才判定服务失健康，避免一次短暂抖动立即触发重启。

需要同时观察两类故障：

- 子进程退出，可通过 `waitpid` 发现；
- 子进程仍存在，但 HTTP health 持续失败。

两种情况都应更新 `ready`、`last_error` 和 restart 计数，让诊断工具能够解释当前状态。

## 重启必须有上限和退避

如果模型文件损坏或设备持续 OOM，无限制立即重启只会形成 crash loop。托管器使用从 `restart_delay` 到 `restart_max_delay` 的退避，并设置窗口或次数上限。

```text
失败 → 等待 1s → 重启
失败 → 等待 2s → 重启
失败 → 等待 4s → 重启
...
超过上限 → 保持失败并上报
```

恢复期间 Agent 仍可保留不依赖 LLM 的确定性命令能力，开放问答则返回可理解的降级提示。

## 用进程组完成退出清理

推理运行时未来可能创建额外工作进程。只向主 PID 发送信号可能留下孤儿，因此启动时建立独立进程组，停止时先请求优雅退出，在 `shutdown_timeout` 内未结束再升级处理，并最终 `waitpid` 回收。

Agent 停止顺序也要明确：停止接收新会话、取消当前 LLM socket、等待工作线程退出、终止推理进程组，最后释放自身资源。析构函数只能作为兜底，不能替代显式生命周期。

## 资源门槛属于正确性

Jetson Orin Nano 8GB 上，相机、ASR、TTS、LLM、Qt UI 和 ROS2 可能同时运行。单独测量 `llama-server` RSS 并不能代表整机安全，验收需要观察进程树、系统可用内存、GPU 资源和长时间峰值。

项目要求全链路压力测试保留至少 1 GiB 可用内存，并区分 x86_64 功能验证与 Jetson 真机结论。若资源不足，选择更小模型、减少上下文或关闭非必要并发，比依赖 OOM 后自动重启更合理。

模型进程托管让故障可以被发现和恢复，但恢复机制不是容量规划的替代品。一个可用的端侧 Agent，既要会回答问题，也要在模型不可用时保持边界清晰、状态可见并安全降级。
