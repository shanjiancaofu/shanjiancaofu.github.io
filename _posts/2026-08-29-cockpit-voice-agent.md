车载语音并不是把录音交给大模型再执行返回结果。它包含唤醒、端点检测、识别、意图路由、动作校验、回复生成和语音播放，其中车辆动作必须保持确定性，生成式模型只能承担开放问答。

## 一条完整的本地语音链路

当前架构把处理流程拆成以下阶段：

```text
ALSA PCM
  → KWS 唤醒词检测
  → VAD / SpeechSegmenter
  → ASR
  → 文本归一化
  → 确定性命令路由
      ├── 命中：TypedAction → Validator → Dispatcher
      └── 未命中：Local LLM → 回复文本 → TTS
```

KWS 持续处理短音频帧；唤醒后 VAD 判断语音开始和结束；完整语音段再交给非流式 ASR。车控只使用最终识别结果，不能根据中间文本提前动作。

## Driver 只负责音频，不理解语音

`audio_driver` 独占 ALSA 采集与播放设备，发布 PCM 并维护设备健康。它不认识唤醒词、Transcript、TTS 或 LLM。

`agent` 消费中立的 PCM 协议，组合 KWS、VAD、ASR、路由、LLM 和 TTS。这样的分工使算法替换不会影响硬件驱动，音频设备变化也不会进入对话逻辑。

采集合同固定为 PCM16、16 kHz、单声道、20 ms 一帧。播放允许根据 TTS 模型使用另一采样率，但 Driver 仍只接收经过大小和格式校验的 PCM，不接受 `Speak(text)` 这种把模型职责带入驱动的接口。

## LLM 为什么不能执行车控

生成式模型的输出不稳定，也可能受到提示注入影响。架构规定 LLM 只生成用户可见文本，不持有 `ActionDispatcher`，不能执行 shell、任意 RPC 或车辆动作。

确定性命令优先经过白名单路由：

```text
“打开相机” → 固定 intent → 类型化参数 → 状态/权限校验 → 动作
“讲个故事” → 未命中车控 → LLM 生成文本
```

这条边界比在提示词中写“请不要执行危险命令”更可靠，因为能力在代码和进程接口上就不存在。

## 半双工先解决回声问题

第一阶段采用半双工：TTS 播放期间暂停 KWS、VAD 与 ASR。否则扬声器播出的回复可能再次被麦克风收进来，触发误唤醒或形成自问自答。

全双工需要回声消除、打断策略和更完整的声学验收。先固定半双工状态机，可以让每次状态变化都可观察：Idle、Waking、Listening、Recognizing、Routing、Thinking、Speaking。

## 模型与运行时必须固定版本

端侧设备启动时不应该临时联网下载模型。运行时、模型文件和配置都要固定版本并校验哈希。项目将 Sherpa-ONNX 模型只放入显式的 Agent 产品构建，默认构建继续使用 mock，避免基础系统无意引入庞大的推理依赖。

本地 LLM 由 `llama-server` 提供服务，但不额外增加 systemd 单元。Agent 负责启动固定二进制、readiness、health、首内容超时、总超时、异常退避重启和退出清理；Navigator 再负责 Agent 进程本身的监管。

## “能够运行”不等于“已经验收”

桌面或 WSL 上通过固定音频 smoke，只能证明接口和模型基本可用。Jetson 真机还要验证麦克风、扬声器、环境噪声、CPU/GPU/内存占用、首字延迟以及长时间稳定性。

测试结论应明确范围：mock 通过、x86_64 fixture 通过、Jetson 实测通过是三种不同证据。把未完成的真机能力标成后续验收，比给出模糊的“已支持”更有价值。

离线语音 Agent 的关键并非把更多模型串起来，而是让数据、资源和权限沿着一条清晰的链路流动。模型负责它擅长的感知与生成，类型化代码负责安全动作，运行时负责故障和资源边界。
