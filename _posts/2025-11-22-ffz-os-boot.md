`ffz-os` 是一个 32 位 x86 学习内核。它从 512 字节的 MBR 开始，经过 Loader 获取内存、建立 GDT、进入保护模式，最后装载 ELF 内核。亲手走一遍这条链路，能把“计算机如何启动操作系统”从概念变成可观察的状态变化。

## BIOS 把第一棒交给 MBR

传统 BIOS 从启动磁盘读取第一个扇区到物理地址 `0x7c00`，检查末尾的 `0x55AA` 标志后开始执行。

MBR 的空间只有 512 字节，其中最后两个字节留给启动签名：

```asm
times 510-($-$$) db 0
db 0x55, 0xaa
```

这段程序只完成最必要的工作：初始化段寄存器和栈、显示启动标记、通过 ATA PIO 读取 Loader，然后跳转到 Loader 入口。

## 使用 LBA 读取 Loader

MBR 通过 `0x1f2` 到 `0x1f7` 端口设置扇区数、LBA 地址和读命令，再轮询硬盘状态。数据准备好后，从 `0x1f0` 端口逐字读取。

一个扇区有 512 字节，而每次 `in ax, dx` 读取 2 字节，因此读取次数是：

```text
扇区数量 × 512 / 2 = 扇区数量 × 256
```

这段代码虽然简单，却已经体现出驱动的基本模式：写控制寄存器、等待设备状态、搬运数据。

## 为什么跳转地址容易出错

项目调试记录中，MBR 最初直接跳到 `LOADER_BASE_ADDR`，但 Loader 文件开头放置了 GDT 和预留数据，真正代码入口在偏移 `0x300` 处。因此跳转需要写成：

```asm
jmp LOADER_BASE_ADDR + 0x300
```

这类错误很典型：二进制已经加载成功，但 CPU 从数据区开始解释指令。排查时需要同时查看链接布局、汇编标签和反汇编结果，不能只看源代码中的函数名。

## Loader 获取物理内存

进入保护模式前，Loader 仍可使用 BIOS 中断。它优先调用 `int 0x15, eax=0xE820` 获取 ARDS 内存区域描述；若失败，再尝试 E801 和 0x88 接口。

这体现了启动代码常见的兼容策略：优先使用信息最完整的接口，同时准备能力较弱的回退路径。内存容量最终保存下来，供内核初始化内存池。

## 进入保护模式的三个动作

从实模式进入保护模式主要包含三步：

1. 打开 A20 地址线；
2. 使用 `lgdt` 加载 GDT；
3. 将 `CR0.PE` 置 1。

随后必须进行一次远跳转，重新装载代码段选择子并刷新流水线：

```asm
mov eax, cr0
or eax, 0x00000001
mov cr0, eax
jmp dword SELECTOR_CODE:p_mode_start

[bits 32]
p_mode_start:
```

如果忘记 `[bits 32]`，汇编器仍可能按 16 位方式编码后续指令，最终机器码与预期不同。这也是项目中实际遇到过的启动故障。

## 从“能跳转”到“能装载内核”

进入保护模式后，Loader 继续读取内核、建立初始页目录、打开分页，并解析 ELF Program Header，将可装载段复制到目标虚拟地址。最后设置内核栈并跳到内核入口。

整个启动过程可以概括为：

```text
BIOS → MBR → Loader → 保护模式 → 分页 → ELF 内核入口
```

启动代码最难的地方往往不是算法，而是每一步都依赖上一阶段留下的寄存器、地址和二进制布局。把每个阶段的输入、输出和 CPU 模式写清楚，是调试早期内核最有效的方法。
